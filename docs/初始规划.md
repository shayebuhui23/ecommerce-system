# 小型电商订单系统（跨境贸易场景扩展版）

## 项目需求与开发计划文档

**文档版本：** V1.0
**项目类型：** 软件工程课程期末综合实践
**项目定位：** 单商家电商订单管理系统，融入适量跨境贸易业务场景
**主要开发方式：** AI 辅助开发，由项目开发负责人统一实现与集成
**计划技术栈：** Vue 3、Element Plus、Java 11、Spring Boot 2.7、MyBatis-Plus、MySQL 8、Sa-Token

# 第一章 项目概述

## 1.1 项目背景

本项目面向小型电商经营场景，构建一套涵盖商品管理、客户管理、购物车、订单处理、模拟支付、库存管理、发货、物流跟踪及售后服务的 Web 应用系统。

传统的简易商城项目通常只实现商品信息的增删改查和简单的订单展示，业务流程较为单薄。本项目以完整订单生命周期为核心，将商品、库存、订单、支付、物流和售后等模块连接起来，重点体现业务规则、状态管理、数据一致性、角色权限及软件测试。

同时，为了兼顾项目开发者对外贸领域的学习需求，系统将适量引入跨境贸易相关场景，包括英文商品资料、客户国家或地区、订单币种、国际收货地址及物流信息等。

本项目不追求真实跨境电商平台的全部能力，而是在课程项目的合理规模内实现可运行、可演示、可测试的业务系统。

## 1.2 项目目标

1. 实现一套具有完整前后端结构的电商订单管理系统。
2. 实现至少三类用户角色及对应的权限控制。
3. 实现不少于八个核心业务功能，避免系统沦为简单的增删改查集合。
4. 建立合理的数据库结构，明确商品、库存、订单、支付记录和售后记录之间的关系。
5. 实现关键业务规则，保证订单状态、库存数量和售后处理之间的一致性。
6. 提供可重复执行的测试数据与测试方法，支持功能验证和缺陷修复。
7. 将有效代码规模控制在课程要求的建议范围内，即约 3000～6000 行。
8. 通过商品资料、国际客户地址、币种和物流等设计，初步了解电商及外贸业务流程。

## 1.3 项目范围

### 本期必须实现

- 用户注册、登录及角色权限管理。
- 商品分类、商品信息和商品上下架。
- 商品查询、筛选与详情展示。
- 购物车及订单创建。
- 库存扣减与恢复。
- 模拟支付及支付结果处理。
- 订单状态管理。
- 发货与物流信息管理。
- 退款申请、审核及处理。
- 商品评价。
- 后台管理与基础经营统计。

### 本期适量扩展

- 商品中文名称、英文名称及英文描述。
- 客户国家或地区、国际收货地址。
- 订单币种与汇率换算展示。
- 国际物流单号及运输状态模拟。
- 商品 SKU、规格与库存管理。

### 本期明确不做

- 真实银行卡、支付宝、微信或国际支付网关接入。
- 真实物流平台 API 接入。
- 真实报关、关税计算及复杂税务处理。
- 多商家入驻与平台分账。
- 复杂优惠券、积分、会员等级体系。
- 复杂促销引擎及分布式架构。
- 生产级高并发、微服务和云原生部署。

以上范围可以根据实际开发进度适当调整，但不得为了增加功能而影响核心流程的正确性。

# 第二章 用户角色与权限需求

系统设置三类角色：普通客户、商家运营人员、系统管理员。

## 2.1 普通客户

普通客户是系统的主要使用者，主要负责商品浏览、购物、订单查看及售后申请。

允许的操作：

- 注册和登录。
- 查看商品分类、商品列表及商品详情。
- 按商品名称、分类及状态筛选商品。
- 添加商品到购物车并调整购买数量。
- 填写收货地址和选择订单币种。
- 创建订单并执行模拟支付。
- 查看个人订单及物流信息。
- 在符合条件时取消订单或申请退款。
- 确认收货。
- 对符合条件的已完成订单进行评价。
- 修改个人资料及收货地址。

限制：

- 只能查看和操作自己的订单。
- 不能修改商品价格、库存和其他客户资料。
- 不能自行将订单标记为已付款或已发货。
- 不能重复提交已经处理完成的退款申请。

## 2.2 商家运营人员

商家运营人员负责商品、库存、订单履约及售后业务。

允许的操作：

- 创建、编辑商品信息。
- 管理商品分类及商品上下架。
- 管理 SKU 和商品库存。
- 查看客户订单。
- 对符合条件的订单进行发货。
- 填写物流公司和物流单号。
- 查看物流及订单状态。
- 审核退款申请。
- 查看商品销售及订单统计。

限制：

- 不能直接修改支付成功记录。
- 不能越权操作不属于自身业务范围的数据；本项目采用单商家模式，但仍须遵守角色权限。
- 不能在订单不满足发货条件时强行发货。
- 不能对同一售后申请重复执行退款处理。

## 2.3 系统管理员

系统管理员负责系统配置、用户管理和运行数据管理。

允许的操作：

- 查看用户列表。
- 启用、禁用用户及管理角色。
- 管理商品分类。
- 查询商品、订单、支付记录及售后记录。
- 查看经营统计数据。
- 查看关键操作审计日志。
- 维护系统币种和汇率等基础配置。

限制：

- 对关键业务数据的修改必须经过明确的业务操作。
- 不允许通过简单修改订单状态绕过正常业务流程。
- 对涉及支付和退款的管理操作应保留操作记录。

## 2.4 权限控制原则

所有权限必须在后端进行校验，不能仅依靠前端隐藏按钮实现权限控制。

系统应验证：

1. 用户是否已登录。
2. 用户是否拥有访问当前功能的角色权限。
3. 用户是否拥有当前订单或相关业务数据的访问权限。
4. 当前业务状态是否允许执行目标操作。

# 第三章 功能需求

## 3.1 用户与认证模块

### 功能说明

实现用户注册、登录、退出登录、个人资料管理及角色权限校验。

### 具体需求

- 用户名或邮箱不得重复。
- 密码应经过安全哈希处理，不以明文存储。
- 登录失败应返回明确但不过度暴露账户信息的提示。
- 登录成功后建立有效的认证状态。
- 普通客户不能自行注册成为管理员或商家运营人员。
- 管理员可以管理用户的启用与禁用状态。
- 被禁用的用户不能继续执行受保护的业务操作。

### 验收标准

- 正确的账户信息能够登录。
- 错误密码不能登录。
- 重复注册的用户名或邮箱被拒绝。
- 普通客户无法调用管理员接口。
- 未登录用户无法调用需要认证的接口。

## 3.2 商品分类与商品管理模块

### 功能说明

实现商品分类维护、商品资料维护、商品上下架和 SKU 库存管理。

### 商品字段建议

- 商品 ID。
- SKU 编码。
- 商品中文名称。
- 商品英文名称。
- 中文商品描述。
- 英文商品描述。
- 商品分类。
- 商品图片地址。
- 商品售价。
- 基础币种。
- 库存数量。
- 商品状态。
- 创建时间和更新时间。

### 具体需求

- 商品必须归属于有效分类。
- 商品价格不得小于或等于零。
- SKU 编码必须唯一。
- 商品下架后不能被加入新订单。
- 库存不得为负数。
- 已被订单引用的商品不应被直接物理删除；可以采用下架或逻辑删除。
- 商品资料修改后，历史订单中的成交价格不得随之变化。

### 验收标准

商家可以创建、编辑、上架和下架商品；客户只能浏览有效商品；无效价格、重复 SKU 和非法库存变更均会被拒绝。

## 3.3 商品浏览与搜索模块

### 功能说明

提供客户浏览商品及筛选商品的能力。

### 具体需求

- 展示商品名称、图片、价格、库存状态等信息。
- 支持按商品名称搜索。
- 支持按商品分类筛选。
- 支持分页查询。
- 支持查看商品详情及中英文商品描述。
- 下架商品不出现在正常商品列表中。
- 商品详情展示的信息应与后台数据一致。

### 验收标准

搜索结果与筛选条件一致，分页数据正确，非法分页参数得到合理处理。

## 3.4 购物车模块

### 功能说明

客户可以将多个商品加入购物车，在下单前调整商品数量。

### 具体需求

- 同一客户的购物车数据相互隔离。
- 可以新增、修改和删除购物车项目。
- 商品数量必须为正整数。
- 不允许添加已下架商品。
- 购物车展示商品当前售价及小计。
- 购物车总金额由后端根据商品数据重新计算。
- 结算前重新校验商品状态、价格及库存。

### 验收标准

修改数量后金额正确更新；非法数量被拒绝；用户不能读取或修改其他客户的购物车。

## 3.5 订单创建模块

### 功能说明

客户从购物车选择商品并提交订单，系统生成订单主记录及商品明细。

### 订单字段建议

- 订单 ID。
- 订单编号。
- 客户 ID。
- 商品明细。
- 购买数量。
- 下单时的商品单价。
- 订单币种。
- 商品金额。
- 运费。
- 订单总金额。
- 收货人信息。
- 国家或地区。
- 完整收货地址。
- 订单状态。
- 创建时间。

### 具体需求

- 订单编号必须唯一。
- 订单金额由后端计算，不能信任前端提交的总金额。
- 商品单价必须保存为订单快照。
- 收货地址应保存为订单快照，避免用户修改地址后影响历史订单。
- 下单时重新验证商品状态及库存。
- 库存不足时不能创建成功订单。
- 订单创建和库存预扣必须在一个可靠的事务流程中完成。
- 客户只能查询自己的订单。

### 验收标准

正常订单能够创建；库存不足时创建失败；重复提交不能产生重复扣减；历史订单价格不受商品后续改价影响。

## 3.6 库存管理模块

### 功能说明

负责商品库存查询、库存扣减和库存恢复。

### 库存规则

- 创建订单时执行库存预扣。
- 库存不足时拒绝下单。
- 订单取消时，根据库存预扣策略恢复库存。
- 退款是否恢复库存应根据订单履约阶段和退款处理结果确定。
- 同一订单不能重复恢复库存。
- 库存变更应记录变更原因、数量和关联订单。
- 所有库存变更必须经过后端业务逻辑处理。

### 技术要求

使用数据库事务和带库存条件的更新语句等方式，保证关键操作的数据一致性。

不允许先读取库存、在业务层无保护地扣减，再假设不会发生并发问题。

### 验收标准

库存不会变成负数；取消订单不会重复增加库存；模拟并发下单时不会出现超卖。

## 3.7 模拟支付模块

### 功能说明

模拟支付成功、失败和支付结果查询，不连接真实支付平台。

### 具体需求

- 只有待付款订单可以发起支付。
- 支付金额必须与订单应付金额一致。
- 支付成功后生成支付记录。
- 支付失败时订单不得变为已付款。
- 重复支付请求不能重复记录成功付款。
- 已取消订单不能再次支付。
- 支付状态与订单状态必须保持一致。
- 管理员可以查询支付记录，但不应直接篡改支付结果。

### 验收标准

支付成功后订单进入已付款状态；失败后状态保持合理；重复支付不会导致订单重复付款。

## 3.8 订单管理模块

### 订单状态

建议使用以下基础状态：

- 待付款。
- 待发货。
- 已发货。
- 已完成。
- 已取消。
- 售后处理中。
- 已退款。

具体状态之间必须存在明确的合法转换规则。

### 主要规则

- 新订单创建后进入待付款。
- 模拟支付成功后进入待发货。
- 商家发货后进入已发货。
- 客户确认收货后进入已完成。
- 符合条件的待付款订单可以取消。
- 退款申请必须经过审核和处理流程。
- 已取消订单不能继续支付或发货。
- 已完成订单不能直接重新进入待发货状态。
- 不允许通过任意修改状态跳过业务校验。

### 验收标准

系统能够拒绝非法状态转换，并记录订单关键状态变更。

## 3.9 发货与物流管理模块

### 功能说明

商家在订单付款成功后进行发货，客户可以查看物流信息。

### 具体需求

- 只有符合发货条件的订单可以发货。
- 发货时必须填写物流公司和物流单号。
- 物流单号不得为空。
- 发货成功后更新订单状态。
- 客户可以查看物流信息。
- 本项目不接入真实物流接口，使用模拟物流状态。
- 物流信息应关联对应订单。

### 跨境业务扩展

物流信息可增加：

- 运输方式。
- 发货国家或地区。
- 目的国家或地区。
- 物流单号。
- 当前运输状态。
- 预计送达日期。

这些信息仅用于业务演示，不代表真实物流服务或实际运输承诺。

## 3.10 售后与退款模块

### 功能说明

客户可以对符合条件的订单申请退款，商家审核后完成模拟退款。

### 具体需求

- 退款申请必须关联有效订单。
- 申请时填写退款原因和说明。
- 系统校验订单状态及退款资格。
- 商家可以审核通过或驳回申请。
- 同一笔订单不能重复完成同一退款操作。
- 退款成功后更新退款记录和订单状态。
- 退款金额不得超过可退款金额。
- 退款处理应避免重复恢复库存。
- 已发货订单的退款处理需要遵循明确的售后规则，不应简单等同于未付款订单取消。

### 简化规则

本期可以不实现复杂的部分退款和多次售后。建议先采用整单退款模型，并明确不同订单状态下的申请条件。

### 验收标准

退款申请、审核、退款结果和订单状态能够正确衔接，重复处理不会产生重复退款或库存错误。

## 3.11 商品评价模块

### 功能说明

客户可以对已完成的订单商品进行评价。

### 具体需求

- 评价必须关联客户、订单和商品。
- 仅满足条件的订单允许评价。
- 评分限定在 1～5 分。
- 评价内容应设置合理长度限制。
- 同一订单商品不得重复提交评价。
- 客户不能删除或修改其他用户的评价。
- 商品详情页可以展示评价信息。

## 3.12 经营统计与后台管理模块

### 统计内容

- 商品总数。
- 上架商品数。
- 订单总数。
- 不同订单状态的数量。
- 已完成订单数量。
- 已完成订单的成交金额。
- 热门商品排行。
- 退款申请数量。

### 统计规则

统计金额应明确采用的币种和统计口径。不同币种的订单不能不经换算就直接相加。

本期可以按订单币种分别统计，或统一换算到指定展示币种，但应明确采用的汇率及计算规则。

# 第四章 跨境贸易场景设计

本章属于在课程候选题目基础上的业务扩展，不要求构建完整的跨境贸易平台。

## 4.1 商品资料国际化

商品资料支持中文和英文名称、描述，便于模拟外贸商品目录的维护方式。

本期不要求完整的多语言后台，也不要求自动翻译。

## 4.2 客户国家或地区

客户可以填写国家或地区、收货人、地址、城市、邮政编码和联系电话。

地址字段应根据国际地址的常见差异合理设计，避免完全依赖中国大陆的固定行政区划格式。

## 4.3 币种与金额

系统至少设置一个基础币种，并允许订单选择项目支持的其他币种。

建议首版支持人民币和美元两种币种，用于模拟不同客户的订单。

金额应使用适合货币计算的十进制类型，避免使用浮点数直接计算金额。

需要明确：

- 商品基础价格采用哪一种币种。
- 订单币种如何确定。
- 汇率来自哪里。
- 汇率何时生效。
- 历史订单是否保留成交时的换算结果。
- 退款金额如何与原订单币种保持一致。

本项目采用管理员维护的模拟汇率，不接实时外汇接口。订单创建时保存采用的汇率及换算结果。

## 4.4 跨境订单信息

订单可以保存客户国家或地区、收货地址、币种、运输方式和物流信息。

不在首版实现报关单生成、海关申报、关税计算、贸易合规审查及真实国际物流接口。

## 4.5 学习价值边界

通过本项目，开发者可以初步了解商品目录、客户资料、订单履约、发货跟踪、售后处理和币种管理。

这些属于电商及外贸业务的基础数字化流程，并不能替代真实外贸工作中涉及的报价、合同、单证、信用风险和贸易规则实践。

- 关键表设置必要的创建时间和更新时间。
- 库存、订单及支付记录应有明确的关联关系。
- 对频繁查询的字段建立合理索引。
- 删除已产生业务记录的数据时，应考虑逻辑删除或保留历史记录。
- 重要的状态变化应有可追溯的记录。

# 第六章 技术架构与项目结构

## 6.1 前端

计划采用 Vue 3、Vite、Element Plus 和 Axios。

前端主要负责：

- 页面展示。
- 表单校验。
- 数据查询和筛选。
- 订单流程交互。
- 角色对应的菜单展示。
- 统一错误提示。

前端不负责决定订单最终金额、支付结果、库存扣减及权限合法性。这些规则必须由后端实现。

## 6.2 后端

计划采用 Java 11、Spring Boot 2.7、MyBatis-Plus 和 Sa-Token。

后端按职责拆分：

- Controller：接收 HTTP 请求并返回响应。
- Service：实现业务规则与事务控制。
- Mapper：执行数据库访问。
- Entity：映射数据库实体。
- DTO：接收请求数据。
- VO：组织响应数据。
- Config：系统配置。
- Exception：统一异常处理。
- Security：认证与权限控制。

## 6.4 接口约定

- 使用 JSON 传输数据。

# 第七章 开发计划

本计划以分阶段交付为原则，具体时间可根据课程截止日期和实际开发进度调整。

## 阶段一：项目初始化

任务：

- 创建前后端工程。
- 配置 Java、Node.js 和 MySQL 环境。
- 建立数据库连接。
- 配置统一响应和异常处理。
- 建立 Git 仓库。
- 完成登录与基础角色权限。

交付标准：

前后端可以正常启动，数据库连接正常，用户可以登录并访问各自允许的页面。

## 阶段二：商品与客户功能

任务：

- 用户资料管理。
- 商品分类与商品管理。
- SKU 与库存基础数据。
- 商品搜索、详情和筛选。
- 收货地址管理。

交付标准：

商家能够维护商品，客户能够正常查询商品，非法参数及越权访问能够被拒绝。

## 阶段三：购物车与订单

任务：

- 购物车管理。
- 订单创建。
- 订单明细快照。
- 库存预扣。
- 订单查询与取消。
- 订单状态转换规则。

交付标准：

客户可以从购物车创建订单；库存不足、重复提交和非法状态转换均得到正确处理。

## 阶段四：支付与履约

任务：

- 模拟支付。
- 支付记录。
- 商家发货。
- 物流信息查询。
- 客户确认收货。

交付标准：

从订单创建到支付、发货、收货的完整流程可以演示，状态与数据保持一致。

## 阶段五：售后与扩展功能

任务：

- 退款申请和审核。
- 商品评价。
- 中英文商品资料。
- 币种和模拟汇率配置。
- 国际收货地址。
- 经营统计及操作日志。

交付标准：

售后流程能够正常执行，历史订单数据不受商品修改影响，跨币种统计有明确的计算规则。

## 阶段六：测试、修复与交付

任务：

- 执行单元测试和接口测试。
- 测试关键业务异常。
- 检查前后端联调结果。
- 修复缺陷。
- 准备测试账号和初始化数据。
- 完善运行说明。
- 统计有效代码行数。

交付标准：

系统能够按照 README 的说明重新部署，核心流程可重复演示，关键测试通过，代码规模符合课程要求。

# 第八章 测试要求

以下测试属于代码实现需要配合的验证内容。测试报告及课程文档由团队按分工整理。

## 8.1 用户及权限测试

- 正确登录与错误密码。
- 重复注册。
- 未登录访问受保护接口。
- 普通客户访问管理员接口。
- 客户访问他人订单。
- 禁用用户继续执行业务操作。

## 8.2 商品及购物车测试

- 商品正常创建和编辑。
- 商品价格为零或负数。
- 重复 SKU。
- 下架商品继续下单。
- 购物车数量为零或负数。
- 购物车金额与后端计算结果不一致。

## 8.3 订单及库存测试

- 正常创建订单。
- 库存不足时创建订单。
- 同一订单重复提交。
- 同一商品被多个请求同时购买。
- 订单取消后库存恢复。
- 重复取消或重复恢复库存。
- 商品改价后历史订单金额保持不变。

## 8.4 支付与售后测试

- 正常模拟支付。
- 支付失败。
- 重复支付。
- 已取消订单再次支付。
- 未付款订单尝试发货。
- 不符合条件的订单申请退款。
- 重复退款。
- 退款金额超出可退款金额。
- 退款处理后库存和订单状态正确。

## 8.5 物流与国际业务测试

- 正常发货及物流查询。
- 缺少物流单号。
- 非法币种。
- 缺少汇率配置。
- 汇率修改后历史订单金额保持稳定。
- 不同币种订单的统计结果符合设定规则。

# 第九章 代码质量与交付标准

## 9.1 代码规模

目标有效代码行数为约 4000～5000 行，最终以实际统计结果为准。

不得通过复制重复逻辑、生成大量空文件或加入无意义注释来凑行数。

优先保证以下业务代码的质量：

- 订单创建与状态流转。
- 库存扣减及恢复。
- 模拟支付与退款。
- 角色权限与数据隔离。
- 关键异常处理。
- 对应的业务测试。

## 9.2 代码质量要求

- 采用清晰的模块划分。
- 避免把全部业务逻辑放在 Controller 中。
- 统一处理异常与参数校验。
- 关键业务操作使用适当的事务管理。
- 不在前端硬编码关键业务结果。
- 不将数据库密码和密钥提交到公开仓库。
- 不使用未经验证的生成代码代替实际测试。
- 对关键业务规则添加必要注释和测试。

## 9.3 Git 管理要求

- 从项目开始就使用 Git。
- 按功能模块分批提交。
- 提交信息明确说明改动内容。
- 修复缺陷时单独提交。
- 不在最后一天一次性提交全部代码。
- 将源码、数据库脚本、运行说明及必要配置纳入仓库。

## 9.4 最终交付物

- 可运行的前端项目。
- 可运行的后端项目。
- 数据库建表脚本。
- 初始化演示数据。
- 主要接口与运行说明。
- 测试代码。
- README 文档。
- 持续、可追溯的 Git 提交记录。

# 第十一章 AI 辅助开发规范

AI 用于辅助代码生成、代码解释、调试、测试用例编写和代码审查，但开发者需要对最终代码负责。

建议采用以下流程：

1. 先明确模块需求、输入输出和业务规则。
2. 先确定数据库结构与接口契约。
3. 按模块实现，不一次生成整个项目。
4. 每完成一个模块就编译、运行并测试。
5. 检查 AI 生成的事务边界、权限控制和异常处理。
6. 对库存、订单、支付及退款逻辑进行重点审查。
7. 对关键代码进行必要的手动修改和验证。
8. 保留真实的开发和 Git 提交记录。

AI 生成的代码不应直接视为正确实现。尤其是库存扣减、重复请求处理、订单状态和退款流程，需要通过实际测试验证。

课程报告应如实说明所使用的 AI 工具及其辅助范围。
