# 全项目审查报告

> 审查对象：`D:\ecommerce-system`（Spring Boot 2.7.18 + MyBatis-Plus + Sa-Token / Vue 3 + Vite + Element Plus）
> 审查范围：**数据库、后端全模块、前端全部页面、配置与部署、工程化**
> 审查方式：全量代码通读 + 运行时实测（后端 8080 / 前端 5173 实跑，真实下单、支付、发货）
> 审查时间：2026-10-18
> 说明：本文取代此前的《订单域审查报告》，并修正其中 3 处误判（见附录 A）。仓库存量文档（README / 交付清单）未纳入本次审查范围。

## 零、结论速览

项目 6519 行前端 + 7776 行后端，分层清晰，**关键的并发防护（重复支付、重复退款、重复发货、库存原子扣减）做得比多数课设扎实**。问题不在"写没写"，而在三处"做了一半"和一处"设计没跟上业务"：

| 类型 | 数量 | 代表问题 |
|---|---|---|
| P0 必修 | 8 | 多商家订单未拆单、SKU 链路断裂、库存无超时释放 |
| P1 业务闭环 | 12 | 已发货仅退款白拿货、退款不进流水、售后 UI 与后端规则冲突 |
| P2 一致性/性能 | 18 | 统计三套口径、每请求 2 次用户查询、汇率不缓存 |
| P3 打磨 | 9 | 3 个单测、6MB 日志、无 lint |

一句话：**"做了一半"的模块（SKU、多商家、币种）比没做的模块更危险**——演示时看着有，一操作就穿帮。

## 一、P0 —— 必修（影响正确性或数据一致性）

### P0-1 多商家订单未拆单（架构级）

**位置**：`OrderServiceImpl.create()` 119-198、`ShipmentServiceImpl.ship()` 60-110、`schema.sql` orders/shipments

**现象**：一张 `orders` 记录只有一个 `status`、一条 `shipments`，但 `order_items` 可以来自任意多个 `seller_id`。

**实测**（订单 18，商品 1 属商家 5、商品 3 属商家 8）：

```
商家5 发货 → 200 发货成功，物流 SF Express/AUDIT-A-0001
商家8 发货 → 1000 只有待发货订单可以发货      ← 它的货永远发不出去
```

**连锁后果**：
1. 任一商家发货即整单 `SHIPPED`，其他商家的货卡死
2. 买家只拿到一条物流单，无法追踪其余包裹
3. 售后按整单退（`AfterSaleServiceImpl:125`），任一商家同意即整单 `REFUNDED`
4. 商家能看到其他商家的商品明细、成本和买家全量信息

**建议**：成本最低是**结算时按商家拆单**（一单一家），改动集中在 `create()` 一个方法：

```java
Map<Long, List<CartItem>> bySeller = cartItems.stream()
    .collect(Collectors.groupingBy(ci ->
        Optional.ofNullable(productMapper.selectById(ci.getProductId()).getSellerId()).orElse(0L)));
if (bySeller.size() > 1) {
    throw new BusinessException(ResultCode.BUSINESS_ERROR, "订单包含多个商家的商品，请分开结算");
}
```

正规做法是引入 `sub_orders(seller_id, status, shipment_id)`，但改动面大，答辩前不建议动。

### P0-2 SKU 链路断裂（表有、实体有、UI 有、中间全断）

**位置**：`CartItemDTO`（无 `skuId`）、`CartServiceImpl:114`、`OrderServiceImpl:138/394`、`ProductDetailDrawer:73-91`

**逐层核对**：

| 层 | 支持 skuId | 说明 |
|---|---|---|
| `product_skus` 表 | ✅ | 4 条演示数据，不同规格不同价 |
| `products` 表 | ⚠️ | 自带 `sku_code` + `price` + `stock`，与 SKU 语义重叠 |
| `CartItem` / `OrderItem` 实体 | ✅ | 有 `skuId` 字段 |
| **`CartItemDTO`** | ❌ | **没有这个字段** ← 断点 1 |
| **`uk_cart_items(cart_id, product_id)`** | ❌ | 不含 sku_id ← 断点 2 |
| `CartServiceImpl` | ❌ | 不读不写，`selectOne(cartId+productId)` |
| `OrderServiceImpl` | ❌ | 用 `product.getPrice()`、`product.getStock()` |
| `buildOrderItem()` | ❌ | 不设 `skuId` / `specName` → **两列永远 NULL** |
| 前端商品详情 | ⚠️ | 只**罗列**规格和价格，**没有任何选择交互** ← 断点 3 |

**实测**：

```
POST /api/cart/items {"productId":1,"quantity":1,"skuId":3}
→ 200 已加入购物车
GET /api/cart → 同一行 quantity 累加到 2，skuId 字段不存在
```

**后果**：
- 选规格完全无效，永远按商品主价结算 → **卖错价**
- 扣的是商品总库存，SKU 库存形同虚设 → **超卖**
- `order_items.sku_id` / `spec_name` 永远为 NULL，订单快照缺规格 → 售后无法核对"买的是哪个规格"

**建议**（4 步，约 120 行）：

1. `CartItemDTO` 加 `Long skuId`（可空 = 默认规格）
2. `uk_cart_items` 改 `(cart_id, product_id, sku_id)`，且 **`sku_id NOT NULL DEFAULT 0`**——MySQL 唯一索引里 NULL 不参与判重，用 NULL 会导致唯一键失效
3. `CartServiceImpl` 按 `productId+skuId` 定位；价格取 SKU，库存取 SKU
4. `buildOrderItem` 补 `setSkuId` / `setSpecName`；`ProductMapper` 加 SKU 级原子扣减

```java
@Update("UPDATE product_skus SET stock = stock - #{qty} WHERE id = #{skuId} AND stock >= #{qty}")
int deductSkuStock(@Param("skuId") Long skuId, @Param("qty") Integer qty);
```

### P0-3 未付款订单永不超时，库存被永久占用

**位置**：全项目无 `@Scheduled` / `@EnableScheduling`；`orders` 无 `expire_at` 列；`OrderServiceImpl:183` 下单即扣库存

**现象**：下单立刻 `deductStock`，之后只能用户主动点"取消"才释放。系统没有任何兜底。

**场景**：用户提交订单去上课，这件货的库存永久 -1。压 100 单，商品直接显示售罄，实际一单没成交。

**建议**：

```sql
ALTER TABLE orders ADD COLUMN `expire_at` DATETIME DEFAULT NULL COMMENT '支付截止时间';
ALTER TABLE orders ADD INDEX `idx_orders_expire` (`status`, `expire_at`);
```

```java
@Scheduled(cron = "0 */5 * * * ?")
public void cancelExpiredOrders() { /* 必须复用 cancel() 的条件更新，不能直接 UPDATE status */ }
```

注意：定时关单**必须走 `cancel()` 同一套条件更新**（`WHERE status='PENDING_PAYMENT'`），否则会和"用户正好在付款"打架。

### P0-4 `sales_count` 下单即计，取消/退款不回退

**位置**：`ProductMapper:20-21` vs `:26-27`

```java
// 扣减：销量一起加
"UPDATE products SET stock = stock - #{q}, sales_count = sales_count + #{q} ..."
// 恢复：只回库存
"UPDATE products SET stock = stock + #{q} WHERE id = #{productId} AND deleted = 0"
```

**实测**：订单还停在 `PENDING_PAYMENT`、一分未付，`sales_count` 已 44→45、28→29。

**后果**：商品页"已售 N 件"虚高；统计页热销榜用的是 `order_items` 累加（第三套口径），两个数字永远对不上。

**建议**（推荐 A）：

| 方案 | 做法 |
|---|---|
| A | `deductStock` 去掉 `sales_count`，改为**支付成功时**自增 |
| B | `restoreStock` 补 `sales_count = GREATEST(sales_count - #{q}, 0)` |

### P0-6 已发货订单「仅退款」= 买家白拿货

**位置**：`AfterSaleServiceImpl:357-366` + `:213-217`

```java
// SHIPPED 状态传 REFUND_ONLY → 允许
return TYPE_RETURN_REFUND.equals(requestedType) ? TYPE_RETURN_REFUND : TYPE_REFUND_ONLY;

// 退款时：只有"没发货"才回库
boolean notShipped = order.getShippedAt() == null;
if (notShipped) restoreOrderStock(order.getId());
```

**链路**：货已寄出 → 买家申请"仅退款" → 商家同意 → 钱退、货不回来、订单变 `REFUNDED`（终态）→ 买家**无法再申请退货**（`REFUNDABLE_STATUS` 不含 `REFUNDED`）。

**建议**：`SHIPPED` 只允许 `RETURN_REFUND`，与 `COMPLETED` 一致：

```java
if (OrderStatus.SHIPPED.name().equals(orderStatus) && TYPE_REFUND_ONLY.equals(requestedType)) {
    throw new BusinessException(ResultCode.BUSINESS_ERROR, "已发货订单请申请退货退款");
}
```

### P0-7 前端没有币种选择，跨境功能实际未接通

**位置**：`CheckoutView.vue:168`（`currency = cartData.currency`）、`:179-183`（`createOrder` 不传 currency）

**现象**：项目定位是"跨境贸易场景"，README 也写"下单时可选 CNY 或 USD"，但**前端没有任何币种切换 UI**：
- 购物车 `currency` 恒为 CNY（后端 `CartServiceImpl:102` 取第一个商品的币种）
- 结算页只读这个值，`submit()` 从不传 `currency`
- 后端 `OrderCreateDTO.currency` 默认 `"CNY"`，于是**所有前端订单都是 CNY**

实测的 USD 订单（order 18）是我直接打 API 造的，界面上走不到这条路。

**建议**：结算页加币种切换（调用 `/api/exchange-rate/list` 拿可选币种），并把 `currency` 带进 `createOrder`。同时 `totalAmount/freightAmount` 需要在前端做汇率换算展示，或由后端提供 `/api/order/preview` 返回双币金额（推荐后者，见 P2-6）。

### P0-8 全局异常处理漏了三类高频异常

**位置**：`GlobalExceptionHandler.java`（139 行，只处理了 7 类）

**缺失**：

| 未处理的异常 | 触发场景 | 现在的结果 |
|---|---|---|
| `DuplicateKeyException` | 订单号同秒碰撞、并发注册同名、并发插售后单 | 500「系统繁忙，请稍后再试」 |
| `HttpMessageNotReadableException` | 前端传了格式错的 JSON / 类型不匹配 | 500 |
| `MethodArgumentTypeMismatchException` | `/api/order/abc` 这类路径参数 | 500 |

**后果**：所有"本可以给出明确提示"的错误，一律变成 500。用户不知道该怎么办，日志里也看不出是业务冲突。

**建议**：

```java
@ExceptionHandler(DuplicateKeyException.class)
public ResponseEntity<Result<Void>> handleDuplicateKey(DuplicateKeyException e) {
    log.warn("唯一约束冲突", e);
    return badRequest("数据已存在或操作过于频繁，请刷新后重试");
}

@ExceptionHandler(HttpMessageNotReadableException.class)
public ResponseEntity<Result<Void>> handleUnreadable(HttpMessageNotReadableException e) {
    return badRequest("请求体格式有误");
}
```

## 二、P1 —— 业务闭环缺失

### P1-1 跨商家越权履约 + 整单信息外泄

**位置**：`ShipmentServiceImpl.ship()` 60-70（**完全没有归属校验**）、`OrderServiceImpl.requireAccessibleOrder()` 447-460

实测商家 8 查商家 5 的订单，能拿到：买家真名 Alex Chen、电话 +1 415 555 0132、完整地址、整单 USD 金额、另一家商品的名称与小计。

**建议**：`ship()` 补 `if (isStaffOnly() && !orderContainsSeller(...)) throw FORBIDDEN`；`detail()` 对 STAFF 裁剪字段（只返回本店 items）。根治靠 P0-1。

顺带发现**同名方法两种语义**：

| 位置 | `items` 为空时 |
|---|---|
| `OrderServiceImpl:479-484` | `return true`（放行） |
| `AfterSaleServiceImpl:438-442` | `return false`（拒绝） |

同一个名字、同一用途，空集合处理相反，建议抽公共方法。

---

### P1-2 商家没有「拒发 / 缺货取消」能力

**位置**：`OrderStatus.cancellable()` 62（只允许 `PENDING_PAYMENT`）

已付款订单，商家库存告急或商品破损时无路可走。现实中会演变成：随便填个假单号 → 买家拒收 → 走售后 → 折腾一圈。

**建议**：新增 `POST /api/order/{id}/seller-cancel`，条件更新 `PENDING_SHIPMENT → CANCELLED`，同时回补库存 + 写退款流水 + 通知买家。

---

### P1-3 退款不进 `payments` 流水，财务对不上账

**位置**：`PaymentServiceImpl:46-47`（status 只有 0/1，无退款态）；`AfterSaleServiceImpl` 全程不碰 `payments`

退款只写 `after_sales`。查"本月实收" = `sum(payments.amount where status=1)`，这个数**不减退款**。

**建议**：`payments` 加 `type('PAY'/'REFUND')` + `refund_of`，退款插一条负数记录；或单独建 `refunds` 表。

---

### P1-4 售后单可并发重复申请

**位置**：`AfterSaleServiceImpl:110-115`（`selectCount` 判重，无唯一约束）

两个请求同时进来都读到 `activeCount=0`，都插入成功。

**建议**（MySQL 8 生成列，`NULL` 不参与唯一性判断，正好只约束"进行中"）：

```sql
ALTER TABLE after_sales
  ADD COLUMN `active_flag` TINYINT GENERATED ALWAYS AS
    (CASE WHEN status IN ('PENDING','WAITING_RETURN','WAITING_RECEIPT') THEN 1 ELSE NULL END) STORED,
  ADD UNIQUE KEY `uk_after_sales_active` (`order_id`, `active_flag`);
```

### P1-5 购物车静默丢弃失效商品

**位置**：`CartServiceImpl:72-84`

`selectBatchIds` 被 `@TableLogic` 过滤掉已删商品 → `productMap.get()` 为 null → `continue`。用户购物车里的商品**凭空消失**，无任何提示，只发现总价变少了。

**建议**：把跳过的项收集进 `CartVO.invalidItems`，前端置灰显示"该商品已下架/已删除"。

### P1-6 多币种商品混买无校验

**位置**：`OrderServiceImpl:124-155`（`totalAmount` 直接相加）、`CartServiceImpl:102`（购物车币种取第一个 item）

`products.currency` 可由管理员设为任意值（`ProductServiceImpl:226`），但下单时一律按 `requireRate("CNY", currency)` 换汇。一个 ¥899 + 一个 $100 → `totalAmount = 999` 当 CNY 换美元。

**当前没暴露**，因为 seed 里 8 个商品全是 CNY。只要运营上架一个 USD 商品，整条链路立刻错。

**建议**：短期在 `addItem` / `create` 校验"购物车内商品币种一致"；长期统一为"商品一律 CNY 标价，结算时选展示币种"。

### P1-7 删除商品会让历史订单"缺商家"

**位置**：`ProductServiceImpl.delete()` 208-214

商品逻辑删除后，`OrderServiceImpl.detail()` 里 `productMap.get()` 为 null → 跳过 `setSellerId` → 订单详情的"商家"一栏空白，`merchants` 列表也少一项。

**建议**：`order_items` 增加 `seller_id` 快照列（下单时写入），订单展示不再依赖商品当前归属。这条同时也解决"商品转移商家导致售后归属错乱"。

### P1-8 下架商品报「库存不足」，提示误导

**位置**：`ProductMapper.deductStock` 的 `AND status = 1`

下架商品结算时，条件更新影响 0 行 → 抛"库存不足，请调整数量"。用户明明看到有货。

**建议**：`create()` 里已有 `status != 1 → "商品已下架"` 的前置校验（131-133），但购物车到结算之间可能刚好下架。扣减失败时区分原因：先查商品状态再决定报错文案。

### P1-9 售后弹窗强制「先确认收货」，还会改写用户选择

**位置**：`AfterSaleDialog.vue:117-143`

```js
if (props.order.status === 'SHIPPED' && !receiptConfirmed.value) {
  // 弹窗要求"请先确认收货"
  await receiveOrder(props.order.id)   // ← 直接把订单改成 COMPLETED
  form.type = 'RETURN_REFUND'          // ← 把用户的"仅退款"强行改成"退货退款"
}
```

**三处问题**：
1. 买家没收到货，却被要求先点"确认收货"才能申请售后，业务上是反的
2. 用户选了"仅退款（未收到/拒收）"，被强制改写为"退货退款"，还得寄回商品
3. 前端只让 SHIPPED 走退货，后端 `resolveType` 又允许 SHIPPED + REFUND_ONLY → **前后端规则冲突**

**建议**：删掉这段强制确认收货逻辑，按 P0-6 统一规则（SHIPPED 只走退货退款），让用户直接提交。

### P1-10 「立即购买」会污染购物车已有数量

**位置**：`ProductDetailDrawer.vue:178-201`

```js
await addToCart({ productId, quantity: 1 })   // 若车里已有 3 件 → 变 4 件
```

### P1-12 管理端「同意退款」一键执行，无二次确认

## 三、P2 —— 一致性、性能与可维护性

| 编号 | 问题 | 位置 | 说明 |
|---|---|---|---|
| P2-1 | **统计营收三套口径** | `StatisticsServiceImpl:178-182 / 194-200 / 233` | 平台用 `sum(base_amount)`（含运费），商家用 `sum(item.subtotal)`（不含运费），热销榜用 `sum(subtotal)` 且**包含 CANCELLED/REFUNDED 订单**。三者互不相等 |
| P2-2 | **成本用当前价，历史利润会被改写** | `:206-231` | `completedCost` 取 `product.getCostPrice()`，商家改一次成本，上月报表跟着变。应在 `order_items` 存 `cost_price` 快照 |
