## 1. Java 程序是怎么跑起来的

### 1.1 和 PHP 的根本差别

PHP 是源码直接交给 PHP-FPM 解释执行，源码即程序。Java 必须先编译成字节码，再由 JVM 加载执行：

```
Java：  User.java  --javac-->  User.class  --java/JVM-->  运行
PHP：   login.php  ----------- PHP-FPM 解释执行 --------->  运行
```

**多出来的"编译"这一层，就是 Java 版本问题比 PHP 复杂得多的根本原因**：PHP 只要解释器版本对得上就行，Java 是编译侧和运行侧两个版本都得对得上。

### 1.2 JDK / JRE / JVM

| 名称 | 全称 | 包含什么 | 说明 |
| --- | --- | --- | --- |
| **JVM** | Java Virtual Machine | 执行字节码的虚拟机 | 是 JDK 的一部分，不单独安装 |
| **JRE** | Java Runtime Environment | JVM + 标准类库 | 只够"运行"，不能编译。**JDK 9 以后不再单独发布**，所以不存在 `jdk-11\jre` 目录 |
| **JDK** | Java Development Kit | javac（编译器）+ java（运行器）+ 标准库 + 工具 | 开发装这个就够了，本项目用 JDK 11 |

### 1.3 版本问题出在哪（重点）

**① class 文件自带版本标记**

javac 编译时会在 `.class` 文件头写一个 major version。JVM 读到比自己新的版本会直接拒绝执行：

```
java.lang.UnsupportedClassVersionError:
  class file version 55.0 (Java 11), this version of the Java Runtime only recognizes
  class file versions up to 52.0 (Java 8)
```

`pom.xml` 里的 `maven.compiler.source/target = 11` 就是告诉 javac"按 11 的标准来编"，编出来的是 major 55。

| Java 版本 | major version |
| --- | --- |
| 8 | 52 |
| 11 | 55 |
| 17 | 61 |
| 21 | 65 |

**② `java` 和 `javac` 可能来自两个不同的 JDK**

命令按 PATH 顺序查找，谁排在前面就用谁。可能出现"`java -version` 显示 11，`mvn -version` 却报 8"这种诡异现象。

**③ 版本在三处各自独立指定，互不联动**

| 指定位置 | 影响谁 | 改法 |
| --- | --- | --- |
| **PATH 顺序** | 命令行敲 `java` / `javac` 实际跑哪个 | 环境变量（本项目已清理完成） |
| **`JAVA_HOME`** | Maven、Gradle、Tomcat 等工具启动时用哪个 JDK | 环境变量 |
| **IDE 的项目 SDK** | 在 IDEA 里点"运行"时用哪个 JDK | IDEA：`File → Project Structure → SDKs` 注册，`Project` 里选用 |

**三者互不联动——系统改对了不代表 IDE 里也对。** 这是新手最容易踩的坑。

### 1.4 本项目三处的正确值（2026-10-16 已核实）

| 检查项 | 期望值 | 实测 |
| --- | --- | --- |
| `java -version` | 11.0.0.2 | ✓ |
| `javac -version` | 11.0.0.2 | ✓（与 java 同目录） |
| `mvn -version` 的 Java version | 11.0.0.2 | ✓ |
| `JAVA_HOME`（系统） | `E:\jdk-11.0.0.2` | ✓ |
| IDEA 已注册 JDK | 11 | ✓（`11 → E:/jdk-11.0.0.2`） |

## 2. Maven

### 2.1 它到底管什么

Maven **不是编译器，也不是 IDE**，它是项目管家，只管两件事：

1. **依赖管理** —— 在 `pom.xml` 里声明要哪些库，它负责下载、缓存、理清版本冲突。
2. **构建流程管理** —— 把"编译 → 测试 → 打包 → 安装"固化成标准阶段，一条命令跑完。

### 2.2 生命周期（理解 Maven 的关键）

Maven 有三条互相独立的生命周期：`clean`（清理）、`default`（构建）、`site`（生成站点文档）。日常只用前两条。

**`default` 生命周期的关键阶段（按顺序）：**

| 阶段 | 做什么 | 产出 |
| --- | --- | --- |
| `compile` | 编译 `src/main/java` | `target/classes/*.class` |
| `test` | 编译并运行 `src/test/java` 下的测试 | 测试报告 |
| `package` | 打包 | `target/*.jar` |
| `verify` | 跑集成检查 | 校验结果 |
| `install` | 装进本地仓库 | 供其他项目依赖 |
| `deploy` | 上传到远程仓库 | （本项目用不到） |

**核心规则：执行某个阶段，会先依次执行它前面的所有阶段。** 所以 `mvn package` 实际上会先跑 `compile` 和 `test`。跳过测试用 `mvn package -DskipTests`。

`clean` 不属于 `default` 生命周期，所以要清理旧产物必须显式写：`mvn clean package`。

### 2.3 依赖解析顺序

```
pom.xml 声明依赖
    ↓
① 本地仓库 ~/.m2/repository  ── 有？→ 直接用，不联网
    ↓ 没有
② 镜像（mirrors 配置）        ── 本项目配阿里云，速度快
    ↓
③ 中央仓库 / pom 中声明的仓库  ── 兜底
    ↓
下载后写入本地仓库，下次复用
```

**依赖冲突的调解规则**（当同一库需要两个版本时）：

- 路径最短优先（直接依赖胜过传递依赖）
- 路径深度相同时，`pom.xml` 里先声明的优先

排查冲突用 `mvn dependency:tree`。

### 2.4 坐标：怎么描述一个库

Maven 用三段式坐标 `groupId:artifactId:version`：

```
org.springframework.boot : spring-boot-starter-web : 2.7.18
      组织/反向域名              模块名            版本号
```

依赖的 `scope`（作用域）常见三种：

| scope | 什么时候可用 | 典型例子 |
| --- | --- | --- |
| `compile`（默认） | 编译 + 测试 + 运行 | 业务代码用到的库 |
| `runtime` | 测试 + 运行，编译时不可见 | MySQL 驱动 |
| `provided` | 编译 + 测试，运行时由外部提供 | Lombok、Servlet API |
| `test` | 只在测试代码里 | JUnit |

### 2.5 镜像（mirrors）

中央仓库在国外，直连慢且容易超时。镜像就是"把它换成国内地址"：

```xml
<mirror>
  <id>aliyunmaven</id>
  <mirrorOf>*</mirrorOf>
  <name>阿里云公共仓库</name>
  <url>https://maven.aliyun.com/repository/public</url>
</mirror>
```

配置位置：`E:\apache-maven-3.6.3\conf\settings.xml` 的 `<mirrors>` 段。

- `<mirrorOf>*</mirrorOf>` 表示接管**所有**仓库请求。优点是快；如果项目需要某个阿里云没有代理的仓库（如 spring-milestones 的里程碑版本）会失败，本项目用的是正式版，不受影响。
- 也可以用 `-s` 参数临时指定另一份 settings 文件，不影响全局配置。

### 2.6 常用命令

| 命令 | 作用 |
| --- | --- |
| `mvn clean` | 删掉 `target/` |
| `mvn compile` | 只编译 |
| `mvn test` | 跑单元测试 |
| `mvn clean package` | 清理 + 编译 + 测试 + 打包，**日常最常用** |
| `mvn clean package -DskipTests` | 同上但跳过测试 |
| `mvn spring-boot:run` | 直接启动 Spring Boot 应用（开发期用） |
| `mvn dependency:tree` | 查看依赖树，排查冲突 |
| `mvn -U clean package` | 强制检查依赖更新 |

### 2.7 与 pip / composer 对照

| Java 世界 | 熟悉的东西 | 说明 |
| --- | --- | --- |
| `pom.xml` | `requirements.txt` + `Makefile` 合体 | **既是依赖清单，也是构建脚本** |
| `mvn` | `pip` + `make` | 装 Maven 自带这条命令 |
| Maven Central | PyPI / Packagist | 官方仓库 |
| `<mirrors>` 阿里云 | 清华 / 阿里 pip 源 | 国内加速 |
| `~/.m2/repository` | `site-packages` / `vendor/` | 本地依赖缓存，跨项目复用 |
| `target/*.jar` | `sdist` 产物 | 可交付文件 |

## 3. Spring / Spring Boot

### 3.1 Spring 的核心：IoC / 依赖注入

传统写法：要用某个类得自己 `new`，而它依赖的其他对象还要先一个个 `new` 好传进去。

Spring 反过来：**你只声明"我需要什么"，容器负责造好、装好、塞给你。** 这叫 IoC（控制反转）/ DI（依赖注入）。

直接好处：类与类之间不再硬绑定，测试时可以轻松替换成 mock 对象。

### 3.2 注解是什么

Java 里"声明"的载体是注解，就是那些 `@` 开头的东西。**把 `@` 理解成"给框架看的标签"，不是业务逻辑。**

| 注解 | 作用 |
| --- | --- |
| `@RestController` | 这个类是 HTTP 接口入口，返回值直接转 JSON |
| `@Service` | 这个类是业务层组件，交给 Spring 管理 |
| `@Mapper` / `@MapperScan` | 这个接口是数据库访问层，由 MyBatis 生成实现 |
| `@Autowired` | 把容器里的对象注入进来 |
| `@RequestMapping` / `@PostMapping` | 绑定 URL 路径 |
| `@Valid` | 触发参数校验 |
| `@SaCheckRole("ADMIN")` | 调用前校验当前用户角色 |
| `@RestControllerAdvice` | 全局异常拦截 |

### 3.3 Spring Boot 在 Spring 上加了什么

| 能力 | 做了什么 | 效果 |
| --- | --- | --- |
| **starter 起步依赖** | 一个坐标带一坨已调好版本的库 | pom 写几行 = 装十几个包 |
| **自动配置** | 按约定默认配好 | 省掉大量 XML |
| **内嵌 Tomcat** | Web 服务器打包进 jar | `java -jar app.jar` 直接就是网站 |

### 3.4 与 ThinkPHP 对照

| ThinkPHP | Spring Boot |
| --- | --- |
| 需要 Apache/Nginx + PHP-FPM，把项目目录丢进去配 vhost | 一个 jar，`java -jar` 就跑，不需要额外 Web 服务器 |
| `composer require` 逐个装包 | starter 一个坐标带一整套 |
| `config/` 目录下的配置文件 | `application.yml` 单文件集中配置 |
| 路由在 `route/` 里定义 | 用 `@RequestMapping` 注解在方法上 |
| 中间件写在 `middleware.php` | 拦截器 + 注解（如 Sa-Token） |
| `Db::name('user')->find()` | `userMapper.selectOne(...)` |

### 3.5 配置文件 `application.yml`

数据库地址、密码、端口、日志级别、MyBatis-Plus 策略、Sa-Token 参数都写这里。

本项目按 `plan.md` 第 46 行的决策：**数据库密码用占位符，真实密码写在 `application-local.yml`（被 `.gitignore` 排除），不提交到仓库。**

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/ecommerce?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
    username: root
    password: ${DB_PASSWORD}     # 占位符，本地覆盖
```

## 4. 分层架构

### 4.1 整体结构

```
Vue 3 前端（浏览器）
      │ HTTP + Token
      ▼
┌─────────────────────────────────────────────┐
│  Spring Boot 应用（1 个 jar，内嵌 Tomcat）    │
│  ┌───────────────────────────────────────┐  │
│  │ Sa-Token 拦截器   先验登录态与角色权限   │  │
│  ├───────────────────────────────────────┤  │
│  │ Controller 层     收参数、返回统一 Result│  │
│  ├───────────────────────────────────────┤  │
│  │ Service 层        业务规则、事务、BCrypt │  │
│  ├───────────────────────────────────────┤  │
│  │ Mapper 层         拼 SQL、读写表         │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
      │ JDBC
      ▼
  MySQL 8（17 张表）
```

### 4.2 各层职责与红线

| 层 | 只做这些 | 绝对不做 |
| --- | --- | --- |
| **Controller** | 接参数、调 Service、封装 `Result` 返回 | **不写业务逻辑**、不直接操作数据库 |
| **Service** | 业务规则、事务控制、密码哈希、组装 VO | 不碰 HTTP 对象（不接 `HttpServletRequest`） |
| **Mapper** | SQL 与对象映射 | 不写业务判断 |
| **Config** | MyBatis-Plus / Sa-Token / CORS / 自动填充配置 | —— |
| **Security** | 鉴权拦截、取当前登录用户 | —— |
| **Exception** | 业务异常定义、全局异常处理 | —— |

**别怕一开始分不清某段逻辑该放哪层。** 判断标准就一条：这段代码是在"处理请求和响应"，还是在"决定业务该怎么走"？前者 Controller，后者 Service。

### 4.3 一次登录的完整走向

1. 登录页填账号密码 → Element Plus 表单校验 → Axios 发 `POST /api/auth/login`
2. Vite 开发服务器把 `/api` 转发到后端 `localhost:8080`（绕过浏览器跨域，配置在 `vite.config.js`）
3. Tomcat 收到请求 → Sa-Token 拦截器发现 `/api/auth/login` 在白名单里 → 放行
4. `AuthController.login(LoginDTO)` 接收 → `@Valid` 触发参数格式校验
5. `UserServiceImpl.login()` 调 MyBatis-Plus 查 `users` 表
6. BCrypt 比对密码哈希；对不上抛 `BusinessException`
7. `GlobalExceptionHandler` 接住异常 → 转成统一的 `{code, message}`
8. 比对通过 → `StpUtil.login(userId)` 生成 token → 返回 `Result<LoginVO>{code, message, data:{token, userInfo}}`
9. 前端 Pinia 把 token 存进 localStorage；Axios 拦截器以后每次请求自动带上
10. 之后访问 `/api/user/page` → Sa-Token 验登录态 + `@SaCheckRole("ADMIN")` 验角色 → 都过了才进 Controller

**关键设计：前端只处理一套错误分支。** 不管出错的是参数校验、密码错误还是无权限，后端都返回同一个 `Result` 结构。

## 5. 组件清单

### 5.1 后端

| 组件 | 是什么 | 在本项目里干什么 | 最接近熟悉的 |
| --- | --- | --- | --- |
| **Spring Boot 2.7.x** | 应用框架 | 提供 Web 容器、依赖注入、配置管理 | ThinkPHP 本体 |
| **MyBatis-Plus** | 半自动 ORM，SQL 自己写、映射自动做 | 查 users 表、分页、逻辑删除、时间字段自动填充 | `Db::name()` |
| **Sa-Token** | 轻量登录鉴权框架 | 登录态管理、`@SaCheckRole` 注解式鉴权 | 自己写的 session 判断 + 中间件 |
| **BCrypt**（spring-security-crypto） | 密码哈希算法 | 密码不明文入库 | `password_hash()` |
| **HikariCP** | 数据库连接池 | Spring Boot 默认自带，无需额外配置 | 长连接复用 |
| **mysql-connector-j** | JDBC 驱动 | Java 连 MySQL 的实现 | PDO 驱动 |

> 说明：JDBC 是 Java 访问数据库的**标准接口**，驱动是它的**具体实现**，二者关系类似 PDO 与 pdo_mysql。

### 5.2 前端

| 组件 | 是什么 | 在本项目里干什么 | 最接近熟悉的 |
| --- | --- | --- | --- |
| **Vue 3** | 前端框架 | 页面与交互 | —— |
| **Vite** | 构建工具 + 开发服务器 | `npm run dev` 起前端，改代码秒刷新 | webpack 的现代替代 |
| **Element Plus** | Vue3 的 UI 组件库 | 登录表单、表格、侧边菜单、消息提示 | Bootstrap / Layui |
| **Pinia** | 状态管理 | 存 token 与当前用户信息，持久化到 localStorage | 全局变量（带持久化） |
| **Vue Router** | 前端路由 | 页面跳转、路由守卫拦截未登录 | 后端路由，只不过跑在浏览器里 |
| **Axios** | HTTP 请求库 | 统一封装请求、自动带 token、统一处理 401/403 | `fetch` / Python `requests` |

### 5.3 前后端分离要点

- 前端是**独立的工程**（`frontend/`），有独立的 `package.json` 和依赖，和 Java 后端没关系。
- 两者只通过 HTTP 接口通信，接口契约见 `plan.md` 的"关键接口契约"章节。
- 开发期由 Vite 代理解决跨域；后端也配了 CORS 作为双保险。

## 7. 开工顺序建议

**别一上来就写业务代码，先把骨架跑空：**

| 步骤 | 做什么 | 验证成功的标志 |
| --- | --- | --- |
| 1 | 建库，执行 `database/schema.sql` 与 `seed.sql` | MySQL 里能看到 17 张表和演示账号 |
| 2 | 搭好后端，`mvn clean package` 能通过 | `target/` 下生成 jar |
| 3 | `mvn spring-boot:run` 启动后端 | 控制台打印 Spring Boot 启动日志、端口 8080 |
| 4 | `npm run dev` 启动前端 | 浏览器能打开页面不报错 |
| 5 | 打通登录接口 | 能登录成功并拿到 token |
| 6 | 再按 `plan.md` 的 6 个任务往下填 | —— |

骨架通了之后，每加一个功能都建在验证过的地基上，出问题容易定位到是哪一层。

| Starter | 起步依赖 | 一个坐标带一整套库 |
| IoC / DI | 控制反转 / 依赖注入 | 对象由框架造，不用自己 new |
| Bean | 容器管理的对象 | 被 Spring 接管的类的实例 |
| ORM | 对象关系映射 | 表 ↔ Java 对象的自动转换 |
| DTO | 数据传输对象 | 接收入参用，如 `LoginDTO` |
| VO | 视图对象 | 返回给前端用，如 `LoginVO` |
| Entity | 实体 | 和数据库表一一对应的类 |
| Mapper | 数据访问层 | 放 SQL 的地方 |
| Token | 令牌 | 登录凭证，前端每次请求带上 |
| CORS | 跨域资源共享 | 浏览器同源策略的放行机制 |
| Hash / BCrypt | 哈希 | 单向加密，密码用它存 |
| JAR | Java 归档包 | 打包产物，可执行 jar 可直接运行 |
